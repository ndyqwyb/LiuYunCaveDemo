# 10 · 工作法与 DevLog

> 项目能不能做完，70% 取决于你有没有稳定的工作节奏。
> 目标：每天打开电脑 30 秒内就知道该做什么，收工时知道今天推进了什么。

## 第一部分 · 日常节奏与任务粒度

### 10.1 每天开工前（5 分钟）

1. **打开 `Docs/DevLog.md`**，读昨天写的「明天第一件事」。
2. **打开 UE，先 Play 一下**，确认当前状态是能跑的（不然后面所有工作都建立在坏状态上）。
3. **写下今天唯一的任务**（只写一件，粒度 1～4 小时）。
4. **把手机静音，关掉 B 站/微信**（你不需要「先看个教程热身」，那是拖延）。

> 🎯 **「今天唯一的任务」是这套工作法最核心的一条。** 不要列 10 项，列了 10 项你一件也做不完，还会有挫败感。**一天推进一件事，12 周就是 84 件事，足够做完这个项目。**

### 10.2 每天收工前（10 分钟）

1. **保存一切**（Ctrl+Shift+S 全部保存）。
2. **Play 一遍**，确认没有新增红色报错。
3. **写 DevLog**（模板见 10.6）。
4. **git commit**：
   ```powershell
   git add .
   git commit -m "M5: rotating bridge angle check fixed"
   ```
5. **关掉 UE 编辑器**（释放内存 + 让 DDC 稳定 + 避免 Live Coding 悬空）。

> ⚠️ **不要「明天再提交」。** UE 项目一天的工作量可能值 2 小时，丢了你会很痛。

### 10.3 每周（1 小时，建议周日晚）

1. **完整通关一次**（哪怕只有白盒），记录问题清单。
2. **整理本周的报错与解决**，形成自己的「踩坑笔记」（这是面试素材）。
3. **备份项目**到移动硬盘 / 网盘（排除 `Saved/`、 `Intermediate/`）。
4. **更新进度截图**到 `Docs/Progress/`。
5. **检查 C 盘空间**（< 40 GB 就清理）。
6. **规划下周的里程碑任务**（把这周没做完的顺延，不要加新东西）。

### 10.4 任务粒度原则（决定你效率的核心）

**每个任务应该能在 1～4 小时内完成，并且有可验证的结果。**

| ❌ 坏任务 | ✅ 好任务 |
| --- | --- |
| 「做风场系统」 | 「让玩家进入 Box 后，Z 速度在 1 秒内平滑升到 1200，并限制不超过 1200」 |
| 「做旋转桥」 | 「按 E 后石柱绕 Z 轴转 90 度，用时 1 秒，转的时候不能再按」 |
| 「做交互系统」 | 「走到火方碑前 300 内，屏幕中央出现『按 E 点燃』，按 E 后消失」 |
| 「做美术」 | 「把 ① 号入口石厅的地板材质换成石砖，UV 缩放调到 4×4」 |
| 「做谜题」 | 「6 个柱子的初始状态设为『灭灭灭灭灭灭』，点第 i 个翻转 i-1/i/i+1」 |

> 🎯 **判断标准**：如果这个任务做完，你能**立刻 Play 看到效果**，它就是好任务。**看不到效果的任务，说明拆得还不够细。**

### 10.5 时间管理（针对「每天只有 1～2 小时」）

| 时长 | 能做什么 | 不能做什么 |
| --- | --- | --- |
| 30 分钟 | 调参数、换材质、写 DevLog、修小 bug | 开始一个新系统 |
| 1 小时 | 写一个 C++ 函数 + 测试、摆一个平台的关卡 | 大重构 |
| 2 小时 | 一个完整的小功能（如「火方碑点亮」） | 设计新系统架构 |
| 4 小时（周末） | 一个完整机关 + 测试 + 提交 | 一次做完整个谜题 |

**原则**：
- **短时间做「不需要长时间思考」的事**（调参、摆关卡、写文档）。
- **长时间做「需要连续专注」的事**（写代码、设计谜题、修复杂 bug）。
- **不要在 30 分钟里试图解决复杂 bug**，那只会让你带着焦虑关电脑。

### 10.6 DevLog 模板（复制粘贴用）

```markdown
### 2026-10-05

- **今天做了**：给旋转桥加了角度对齐判定，转到 90 度时能接通光路。
- **卡在哪 / 怎么解决**：一开始用 `==` 比较角度死活不通，改成
  `FindDeltaAngleDegrees < 5.0f` 后正常。记住：浮点数不能直接比相等。
- **明天第一件事**：给旋转中的石柱加「禁止重复交互」。
- **今天的状态**：😀 顺利 / 😐 一般 / 😫 卡住
```

> 💡 **「卡在哪 / 怎么解决」这一栏最重要。** 三个月后它就是你的面试故事库。

### 10.7 进度可视化（对抗「看不到成果」）

在 `Docs/Progress/` 下维护一个 `PROGRESS.md`：

```markdown
# 进度看板

## 里程碑
- [x] M0 环境地基
- [x] M1 玩家手感
- [ ] M2 白盒关卡 ← 当前
- [ ] M3 交互系统
...

## 截图
- M1: ![](M1_player.png)
- M2: ![](M2_blockout_top.png)
```

**每周更新一次**。当你觉得「我好像没做什么」时，翻这个文件，你会发现自己已经走了很远。

## 第二部分 · 进度可视化与心态

### 10.8 「状态不好」的时候怎么办

| 状态 | 建议做的事 |
| --- | --- |
| 累，不想动脑 | 摆关卡、换材质、整理文件夹、写 DevLog |
| 卡住，烦躁 | 离开电脑走动 15 分钟；回来用 `09_风险与踩坑速查.md` 流程排查 |
| 觉得无聊 | 做点「马上能看到效果」的事（调光照、加 VFX） |
| 想放弃 | 看 M1 的截图，想想那时候你连项目都建不起来 |
| 太兴奋想加功能 | 打开 `01_项目定位与版权合规.md`「不做清单」，冷静 10 分钟 |

> 🎯 **每周至少休息一天。** 这不是懒惰，是为了让你能坚持 12 周，而不是 3 周后彻底burn out。

## ✅ 本章验收标准

- [ ] 已建立每天开工/收工的固定动作（5 分钟 + 10 分钟）
- [ ] 每天只写一个“今天唯一任务”，粒度 1～4 小时、可玩到效果
- [ ] 每天收工前写 3 行 DevLog + git commit
- [ ] 每周至少休息一天，避免 3 周后彻底 burn out

## 🐛 常见坑

| 坑 | 后果 | 正确做法 |
|---|---|---|
| 一天列 10 个任务 | 一件也做不完，挫败感强 | 只写今天唯一任务 |
| 任务太大（“做风场系统”） | 无法验收 | 拆到“能 Play 看到效果” |
| 不提交就关电脑 | 丢一天工作 | 每天收工前 commit |
| 状态不好还硬写复杂代码 | 越写越乱 | 状态不好只摆关卡/整理文件 |
