## 卷首 · 三条使用规则

1. **每周日晚上花 1 小时**读下周清单：把任务抄进 `DevLog.md`，估一下时间，删掉明显做不完的。
2. **每完成一项就打勾**（在本文档里直接改 `[ ]` → `[x]`）。进度可视化是对抗「看不到成果」的唯一办法。
3. **到验收标准就停手，不进下一项。** 新手最大的时间黑洞是「顺便再优化一下」。**验收清单是刹车，不是起点。**

> ⚠️ **如果某周落后了：砍美术，不砍玩法。** 玩法完整、画面朴素 > 画面漂亮、玩法残缺（尤其对 Gameplay 岗位）。

## 第 1 周 · 地基周（M0 + M1 前半）

### 🎯 本周目标

让**一个空的 C++ 项目**能编译、能打包、能进 Git。这一步不做完，后面全是空中楼阁。

### ✅ 任务清单

**M0 · 环境地基（先做，别跳）**

- [ ] 清理 C 盘，腾出 **40 GB 以上**（详见主企划案第 13.1 节）
- [ ] 把 **DDC（派生数据缓存）** 迁到 E 盘（第 13.2 节）
- [ ] 用 UE 5.5 创建 **C++ 项目** `LiuYun`，路径 `E:\UE_projects\LiuYun`
- [ ] 确认 `LiuYun.uproject` 生成成功，且能在 VS 2022 里打开
- [ ] **首次编译成功**（这一步最容易卡住，预留半天）
- [ ] 跑一次 Live Coding（在编辑器里改一行 C++，看它热编译）
- [ ] Git 初始化 + `.gitignore` + **Git LFS 配置**（第 13.5 节）
- [ ] 第一次提交：`git commit -m "M0: 项目初始化"`
- [ ] 显卡设置：强制使用 RTX 4060 运行 UE（第 13.6 节）
- [ ] **🎯 打一次包（Shipping 或 Development）并成功运行** ← **本周最重要的一项**
- [ ] `git tag M0`

**M1 前半 · 玩家手感**

- [ ] 打开第三人称模板地图，玩 5 分钟，感受移动/跳跃/镜头
- [ ] 弄清模板角色的组成：`CharacterMovement` + `SpringArm` + `Camera`
- [ ] 新建 `ALY_PlayerCharacter`（继承模板角色，**不要删模板类**）
- [ ] 新建 `BP_LY_PlayerCharacter`（继承 `ALY_PlayerCharacter`）
- [ ] 把输入资产重命名为 `IMC_LY_Default` / `IA_LY_*`
- [ ] 调第一轮参数：移动速度、跳跃高度、相机臂长

### 📏 验收标准（全部打勾才算过关）

- [ ] 关掉编辑器后，双击 `LiuYun.uproject` 能正常打开
- [ ] 在 **VS 里按 F5** 能启动编辑器（不是只能用 Epic Launcher 打开）
- [ ] **打包产物在自己的电脑上双击能运行**（不是只在自己编辑器里能跑）
- [ ] `git log` 能看到 M0 的提交，`git tag` 能看到 `M0`
- [ ] 在编辑器里 Play 能控制角色走动、跳、转视角

> ⚠️ **M0 的打包验证不许跳过。** 这是全项目最重要的一次「压力测试」。很多新手把打包拖到第 12 周，结果发现要重装工具链，直接崩盘。

### 🐛 本周常见卡点速查

| 症状 | 原因 | 解决 |
| --- | --- | --- |
| 右键没有「Generate Visual Studio project files」 | 没装对 UE 的右键菜单集成 | 从 `.uproject` 右键菜单或用 UE 的 Generate 工具；或先确认引擎已关联 |
| 编译报 MSVC 版本不匹配 | VS 装了但没装对组件 | 用 VS Installer 勾「使用 C++ 的游戏开发」工作负载 + Windows SDK |
| 首次编译超慢 / 卡住 | 正常现象 | 第一次要编译引擎相关的很多文件，**耐心等**，去看一眼任务管理器 |
| 打包失败，报缺 SDK | Windows SDK 没装或版本不对 | 用 VS Installer 勾对应 Windows SDK |
| 编辑器能跑、打包后黑屏 | 默认地图没设 | `Project Settings → Maps & Modes` 设 Default Map |
| C 盘又满了 | DDC 还在默认位置 | 回到第 13.2 节，把 DDC 指到 E 盘 |

### 📦 本周产出

- `LiuYun.uproject` + Git 仓库 + 一次成功的打包 + `ALY_PlayerCharacter` 雏形

**M2 前半 · 白盒开局**

- [ ] 按主企划案第 5.2 节的**尺度规范**搭**第 1、2 座平台**（入口石厅 + 旋转桥平台）

### 📏 验收标准

- [ ] 连续跳 20 次不觉得别扭
- [ ] 镜头不穿墙、不卡在几何体里
- [ ] 从入口平台能走到旋转桥平台
- [ ] 掉下平台会触发死亡/重生（不是无限下坠）

### 🐛 本周常见卡点速查

| 症状 | 原因 | 解决 |
| --- | --- | --- |
| 输入完全没反应 | IMC 没挂到 PlayerController / Character 上 | 检查 `IMC_LY_Default` 是否在 BeginPlay 里 AddMappingContext |
| 角色滑动/停不下来 | 移动参数太高 + 摩擦力太低 | 调 `Braking Deceleration` / `Ground Friction` |
| 掉下去无限下坠 | 没设 Kill Z | `World Settings → Kill Z` 设一个合理高度 |
| 镜头晕 | 相机臂太短 + 灵敏度太高 | 臂长加长到 300～400，降低灵敏度 |
| 灰盒搭得太大/太小 | 没按尺度规范，凭感觉 | 回到第 5.2 节，**用角色身高当尺子**量 |

- 手感定稿的玩家角色 + 2 座平台的灰盒 + 30 秒走路视频

### 📏 验收标准

- [ ] 连续快速点击旋转 20 次，状态不乱

- [ ] 谜题的视觉提示**足够清楚**（玩家知道「现在该我按了」）

### 🔑 本周核心技术点：角度对齐判定

```cpp
// ❌ 错误做法：浮点数永远不会正好相等
if (CurrentAngle == TargetAngle) { /* 永远进不来 */ }

// ✅ 正确做法：算角度差，给容差
const float Delta = FMath::Abs(FMath::FindDeltaAngleDegrees(CurrentAngle, TargetAngle));
if (Delta < 5.0f) { /* 对齐成功 */ }
```

> ⚠️ **这是全项目最著名的坑，也是面试可以讲的故事。**
> 先用调试输出把角度打在屏幕上，**看着它转**，你就瞬间理解了。**这半天不能省。**

### 🐛 本周常见卡点速查

| 症状 | 原因 | 解决 |
| --- | --- | --- |
| 光路怎么都接不通 | 浮点数直接比较 | 用 `FindDeltaAngleDegrees` + 容差 |
| 光路亮了但走不上去 | 碰撞体没跟着切换 | 光路状态变化时同步 SetCollisionEnabled |
| 转一下触发好几次 | 旋转过程中仍然响应输入 | 加 `bIsRotating` 状态锁 |
| 序列播放和玩家输入冲突 | 时序没管好 | 加 `EPuzzleState`（Idle/Playing/Input/Result），不同状态处理不同输入 |
| 谜题无解 | 初始状态设计错了 | **先在纸上推演**，确定有解再写代码 |
| 玩家卡死无法重来 | 没做重置 | 加一个「重置」交互点或超时自动重置 |

### 📦 本周产出

- 可用的旋转光桥（含对齐判定与碰撞）+ 记忆顺序谜题（三轮可通）

- [ ] 点一个柱子，**自己和左右相邻**三个的视觉同时变化
- [ ] 全亮后光路直通终点，玩家能走过去
- [ ] 进风场后**稳定上升**，速度不失控
- [ ] **不会飞出地图**，到顶后能正常落到平台上
- [ ] 在风场边缘来回走不会抖动/闪

### 🔑 本周核心技术点

**环形数组的左右索引（必须取模）：**

```cpp
const int32 Left  = (Index - 1 + Count) % Count;   // 不加 Count 会变负数！
const int32 Right = (Index + 1) % Count;
```

**风场的正确实现思路：**

```
进入风场体积 → 每帧给角色一个向上的速度（不是 AddForce）
              → 用 FMath::Min 限制最大上升速度
离开体积     → 恢复角色自己的重力
```

- **不要用 `AddForce`**：物理力会累积，玩家会越飞越快、直接飞出地图。
- **直接设速度更可控**：`Velocity.Z = FMath::Min(Velocity.Z + Accel * DeltaTime, MaxRiseSpeed);`

> 💡 **原版 D→E 是「风场 + 滑翔」，本 Demo 删掉滑翔后改成「气流电梯」。**
> 玩家进风场是被动上升，到顶后被推到平台上。**这个改动让 D→E 更简单，也更适合初学者。**

### 🐛 本周常见卡点速查

| 症状 | 原因 | 解决 |
| --- | --- | --- |
| 数组越界崩溃 | 没做取模，负数索引 | 用上面的 `(Index - 1 + Count) % Count` |
| 谜题永远无解 | 初始状态是死局 | **纸上推演**；或先用「全灭」当初始状态 |
| 谜题太简单 | 只用 6 个柱子、初始全灭 | 调整初始亮灭模式增加步数 |
| 玩家越飞越快、飞出地图 | 用了 AddForce | 改成直接设速度 + 上限 |
| 风场边缘抖动 | 在重叠边界反复进出 | 加迟滞阈值（0.2 秒宽限） |
| 到顶后掉下去 | 顶端没有平台或推出力不够 | 顶端加一个平台 + 给一个向前的水平速度 |

### 📦 本周产出

- 联动翻转谜题（有解、可重置）+ 风场电梯

# 第四部分 · 面试模拟问答（Gameplay 程序方向）

> **使用方式**：打印出来，**对着镜子或录音练**。不要背逐字稿，要练到「能自然说出来」。
> 每题给的是**要点骨架**，你要用自己的话填进去。主企划案第 19.5 节给了 5 题的完整示范稿。

## 4.1 必答题（一定会问，准备到能脱口而出）

### Q1 ·「介绍一下你这个项目」

**回答骨架**：
- 一句话定位：「UE5 C++ + 蓝图复刻的原神璃月秘境垂直切片，10 分钟解谜，无战斗」
- 我做了什么：「12 周，从环境搭建、白盒、机关系统到美术替换打包」
- 技术重点：「**蓝图与 C++ 的协作架构**：所有机关继承同一 C++ 基类，接口 + 事件广播解耦，蓝图只负责表现」
- 收尾：「新增机关只需继承基类 + 配参数 + 做蓝图表现，逻辑零重复」

### Q2 ·「为什么用原创/免费素材代替官方资产？」⭐ 加分题

**回答骨架**：
- 「这是有意为之」——不是「我不会建模所以凑合」
- 两条理由：① 提取官方资产有版权风险，**我投的是米哈游，更要避免**；② 我的目标是练 gameplay 和工程，美术不是重点
- 「我把时间集中在玩法上，美术用免费素材和 AI 生成，全部记录在 AssetCredits 里」
- 金句：「**能清楚说明『为什么不那么做』，也是工程判断力的一部分。**」

### Q3 ·「蓝图和 C++ 你怎么分工？」⭐ 核心题

**回答骨架**：
- 一句话原则：「**C++ 定规则，蓝图做表现，关卡摆实例**」
- C++ 负责：玩家角色、交互检测、机关基类与状态机、谜题算法、关卡流程总控
- 蓝图负责：材质切换、Niagara 特效、音效、UI 动画
- 关卡负责：摆放机关、配置实例参数（如方碑编号）
- 判断标准：「**需要复用/需要测试/连线成一坨的 → C++；美术表现和数值调参 → 蓝图**」
- 举例：`ALY_MechanicBase` 统一状态和事件，子类只写差异逻辑，总控能统一监听所有机关

### Q4 ·「两处谜题的设计你能讲讲吗？」⭐ 展示设计能力

**回答骨架**：
- 先抛洞察：「这个关卡有**两处完全不同的火柱谜题**，很多攻略会混淆，这是我考据时发现的」
- 第一处：**记忆顺序型** —— 播放序列、玩家复现、三轮递增，考观察力和记忆
- 第二处：**联动翻转型** —— 六柱成环、点一个翻三个、目标全亮，是**有解的数学谜题**
- 实现：「第一处用 Manager 管序列状态和校验；第二处用环形数组 + 取模索引 + 全亮判定」
- 收尾：「**两处共用同一套火方碑基类，只是上层 Manager 不同，这就是抽象的价值**」

### Q5 ·「你遇到最大的困难是什么？」⭐ 展示成长性

**回答骨架**：
- 选**旋转光桥的角度对齐**（真实、具体、有技术含量）
- 「一开始用浮点数直接比较角度，怎么写都接不通，debug 了一整天」
- 「后来意识到浮点数不能直接比相等，改成算角度差 + 容差，立刻就通了」
- 升华：「这让我理解了**『物理/几何的边界情况比主逻辑更容易出问题』**，后来做风场、移动平台我都会先考虑边界情况」
- 收尾：「我把这些问题都记在 DevLog 里，**它们反而是我成长最快的部分**」

## 4.2 进阶题（大概率会问，准备要点）

| 问题 | 回答要点 |
| --- | --- |
| **为什么用事件广播而不是直接调用？** | 解耦：机关不需要知道谁在听；总控、UI、音效、成就系统都能独立订阅；新增监听者不用改机关代码 |
| **为什么机关要抽象成基类？** | 统一状态和生命周期（未激活/激活/完成），总控可以统一管理；新增机关代码量 < 100 行 |
| **碰撞通道怎么设计的？** | 有专门的 `LY_Interactable` 通道，交互射线只查这个通道，避免打到地形/角色 |
| **风场为什么不用 AddForce？** | 物理力会累积导致失控；直接设速度 + `FMath::Min` 上限更可控、更好调 |
| **移动平台怎么让玩家跟着走？** | 速度传递或 Attach；关键是转身/跳离时的状态清理 |
| **检查点怎么防止顺序错乱？** | 检查点带索引，只接受「比当前更新的」检查点 |
| **性能怎么优化的？** | `stat unit` 找瓶颈；动态光源 ≤ 8；Lumen 质量降档；材质实例复用 |
| **为什么不做战斗？** | 主动的范围控制：目标是练关卡与机关系统；加战斗会稀释深度，且美术成本高 |
| **怎么保证不同机关手感一致？** | 统一视觉语义（可交互=青蓝呼吸光、已激活=金色稳定光）+ 统一交互距离与反馈时长 |
| **如果让你重做，你会改什么？** | 选一个**真实的**改进点，例如「更早做打包验证」「更早找人试玩」「机关参数外置成 DataAsset」 |

## 4.3 陷阱题 / 压力题（小心，容易翻车）

| 问题 | ⚠️ 错误回答 | ✅ 正确回答 |
| --- | --- | --- |
| **「这是原神的关卡，不算你的设计吧？」** | 辩解「我改了很多」 | 「关卡结构是参考，但**机关系统的技术实现、C++ 架构、8 阶段流程控制、两处谜题的算法**都是我自己设计和实现的。我把它当成**用真实关卡作为需求**的一次工程练习。」 |
| **「美术这么简陋，是不是偷懒？」** | 「我不会建模」 | 「这是**有意识的取舍**。我投的是 gameplay 方向，所以把时间预算集中在玩法与架构上。美术用统一色板 + 后处理描边 + 免费素材，做到**风格统一、能代表完成度**就够了。」 |
| **「这不就是照着教程做的？」** | 含糊其辞 | 直接讲**哪个部分是自己想的**：谜题算法的抽象、环形取模、风场速度控制、检查点索引设计。**诚实 + 具体**最有说服力 |
| **「C++ 写了多少行？」** | 编一个数字 | 说**实际的类和职责**：「十来个 C++ 类，玩家角色、交互组件、机关基类、六个机关子类、两个谜题 Manager、流程总控」——**比行数更有说服力** |
| **「你能现场改个功能吗？」** | 慌张拒绝 | 「可以，给我一个具体需求」——**这是展示能力的机会，不是陷阱**。现场演示是你最大的优势 |

## 4.4 你还应该反问面试官的问题（展示你认真思考过）

# 第五部分 · 应急路线与心理建设

## 5.1 如果进度落后了，按这个顺序砍（主企划案第 15.4 节）

**砍的顺序（从先砍到后砍）：**

1. ❌ 美术精细化（建筑模块细节、道具外观）
2. ❌ VFX 的复杂度（火焰/风用最简单模板）
3. ❌ UI 美化（用默认风格，能看懂就行）
4. ❌ 音频（**只留环境音 + 3 个机关音效**）
5. ❌ 终点演出的复杂度（改成简单对话框）
6. ❌ 角色外观（用最简单的人形占位）
7. ⚠️ 只保留 **3 个宝箱**
8. ⚠️ 只保留**一个旋转桥**（第二个改成自动开门）

**绝对不砍：**

- ✅ M0 的打包验证
- ✅ 玩家手感
- ✅ 交互系统
- ✅ 旋转光桥（核心机关）
- ✅ 两处谜题的**逻辑**（可以简化参数，但机制要在）
- ✅ 完整流程（从入口走到结算）
- ✅ 合规声明与 AssetCredits

> 🎯 **一句话原则：砍「看起来」的部分，保「玩起来」的部分。**

## 5.2 如果只剩 6 周就要投简历（应急交付路线）

| 周 | 做什么 |
| --- | --- |
| 第 1 周 | M0 + M1（环境 + 手感），**必须完成打包验证** |
| 第 2 周 | M2 白盒（简化：4 座平台而非 6 座）+ M3 交互 |
| 第 3 周 | M4 + M5（火方碑 + 旋转桥） |
| 第 4 周 | M6 + M7（**只做联动谜题**，砍掉记忆谜题；风场用最简单的上推体积） |
| 第 5 周 | M8 组装 + **只做天空/雾/地板/光路四样美术** |
| 第 6 周 | 打包 + 录视频 + 写 README + 技术文档 |

> 💡 这条路线产出的作品集**依然是合格的**：核心机关在、完整流程在、C++/蓝图分工能讲清楚。
> **完整性 > 复杂度。** 一个 8 分钟能通关的简化版，比一个 20 分钟但走不完的版本强得多。

## 5.3 「状态不好」的时候怎么办（主企划案第 16.5 节）

| 症状 | 应对 |
| --- | --- |
| 连续几天不想打开 UE | **降低门槛**：今天只做「打开项目、随便走两圈」也算完成任务 |
| 觉得做得太丑，想推倒重来 | **回看 `Docs/Progress/` 的早期截图**，你会发现自己进步很大 |
| 卡在一个 bug 上两天了 | **立刻换任务**，去做别的部分；或者把问题写进 DevLog 明天再看 |
| 觉得自己根本做不完 | **看第 8 周的应急路线**：你随时可以在任何一周停下，产出一个完整可玩的东西 |
| 怀疑这个项目对求职没用 | 回看本文件第四部分 —— **你练的这些恰恰是 Gameplay 岗最想看的** |
| 想再加一个功能 | **回去读 README 的「不做清单」**。范围膨胀是这类项目的头号杀手 |

> 💡 **这个项目的难点从来不是技术，而是「坚持到完整可玩」。**
> 你不需要做得比原神好，你只需要**做完** —— 做完本身就是极强的信号。

## 5.4 项目结束后（主企划案第 20.5 节）

1. **先玩一周不碰 UE。** 让脑子冷却。
2. 把这 12 周的 DevLog **从头读一遍**，把「遇到的坑 + 怎么解决」整理成一篇技术博客/知乎回答 —— **这是你简历之外的第二个作品**。
3. 复盘：哪些地方浪费时间了？哪些决策是对的？
4. **下一个项目换一个方向**：这次练了「机关解谜系统」，下次可以练「AI 行为树」「战斗系统」「存档系统」—— **广度是求职的加分项**。
5. 把本项目的 C++ 类**重构成一个可复用的插件**，作为长期资产。
