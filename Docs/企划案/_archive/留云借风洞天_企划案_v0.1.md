## 1. 项目概述

### 1.1 一句话目标

用 UE5，以 C++ 为骨架、蓝图为血肉，复刻《原神》璃月魔神任务第一章第一幕中「留云借风洞天」的秘境挑战流程，产出一个**可完整通关的 10～20 分钟垂直切片（Vertical Slice）**。

### 1.2 为什么选这个关卡作为学习项目（它非常适合你）

这个秘境作为第一个完整项目，客观上是个**聪明的选择**，原因：

1. **空间封闭**：不用做开放世界、不用做大地图流送（World Partition）、不用担心远景优化。
2. **机制驱动**：核心是"风场 + 滑翔 + 机关 + 移动平台"，都是可以逐个攻克的小系统，没有复杂战斗 AI 和元素反应。
3. **垂直结构**：天然是分层的，可以一层一层做，做完一层就能玩一层，成就感来得快。
4. **有明确终点**：有 BOSS 房式的终点（顶层对话/出口），有天然的验收标准。
5. **美术需求可控**：室内洞天，光源少、遮挡多、不用做天气和昼夜。

### 1.3 成功标准（Definition of Done）

只有全部满足，才算这个 demo 做完了：

- [ ] 玩家从入口开始，能一路通关到终点，**中途不需要打开编辑器**。
- [ ] 至少 4 种机关能正确工作：风场、移动平台、激活式机关、联动开门。
- [ ] 掉出地图 / 卡死时，能自动回到最近的检查点。
- [ ] 有最基本的目标提示 UI（当前该干什么）和交互提示（按 E 交互）。
- [ ] 全关卡美术资源替换完毕，玩家看不出"这是灰盒"。
- [ ] 在你自己机器上运行稳定 60 FPS（RTX 4060 Laptop / 1080p）。
- [ ] 项目已进版本控制（Git + LFS），有 README 和一键启动说明。
- [ ] 打出一个能双击运行的打包版本（Development 或 Shipping）。

### 1.4 明确【不做】的事（这条比"要做"更重要）

初学者项目 90% 的死法不是"没做完"，而是"想要的太多，最后每个都是半成品"。

**本 demo 明确不做：**

| 不做的东西 | 为什么不做 |
| --- | --- |
| 开放世界 / 大地图 | 与学习目标无关，工作量是 100 倍 |
| 完整战斗系统（元素反应、角色切换、武器） | 需要 GAS + 数值 + AI + 动画，是另一个完整项目 |
| 联网 / 多人 | 需要网络同步、专用服务器概念，零收益 |
| 完整角色系统（抽卡、队伍、背包） | 与"秘境复刻"无关 |
| 移动端 / 主机适配 | 增加打包与性能负担 |
| 从零写自研引擎级系统（如自研滑翔物理） | 先用引擎现成能力，够用就行 |
| 像素级还原原神美术 | 你一个人做不出米哈游的美术，别跟自己较劲 |

**"不做"清单要写进项目的 README 里，** 每次你心痒的时候回去看一眼。

### 2.2 三个必须立刻处理的环境问题

**🔴 问题 1：C 盘只剩 11.5 GB，会被 UE 撑爆**

UE5 会自动把「派生数据缓存（DerivedDataCache，简称 DDC）」写到 C 盘用户目录，做这个项目很容易占 30～80 GB。C 盘爆满会导致引擎莫名其妙崩溃、编译失败、系统卡死。

解决（在第 12.3 节有逐步操作）：把 DDC、着色器缓存、资产临时目录全部改到 E 盘。

**🟡 问题 2：Visual Studio 17.14 + MSVC 14.44 可能对 UE 5.5 过新**

UE 5.5 官方验证过的 MSVC 版本大约是 14.38 左右。14.44 可能触发编译警告甚至报错（UE 对编译器版本检查很严格）。

解决：优先让 UE 使用 14.36 工具链，或在项目里限制编译器版本。第 12.4 节给了三种做法。

**🟡 问题 3：双显卡（780M 核显 + 4060 独显）**

笔记本的双显卡会导致：编辑器用核显渲染（卡顿）、打包后跑不起来、GPU 崩溃。
解决：NVIDIA 控制面板里把 UnrealEditor.exe 和 UE5Editor 进程强制设为「高性能 NVIDIA 处理器」；Windows 图形设置里也给 UnrealEditor.exe 指定独显。

### 2.4 你的学习路线（不要在项目中途停下学三个月理论）

**错误的做法：** 先看 3 个月教程，再开始做。
**正确的做法：** 在做项目的过程中"按需学习"，每个里程碑前学 2～4 小时刚好够用的知识。

我建议的**前置速成**（正式开项目前，总共约 12～16 小时）：

1. **UE 编辑器生存技能**（3 小时）：视口导航、Actor 概念、大纲视图、细节面板、内容浏览器、保存与重命名资产。
2. **C++ 极简语法**（4 小时）：变量、函数、if/for、类、继承、指针与引用、头文件与源文件。**不要学模板、STL、多线程。**
3. **UE C++ 第一个类**（2 小时）：用编辑器新建一个 C++ Actor，在 BeginPlay 里打印一句话，编译，拖进关卡，看到输出。这一步跨过去，后面就顺了。
4. **蓝图速通**（3 小时）：变量、事件、函数、宏、Cast、常用节点（Delay/Timeline/SpawnActor）。
5. **Git + LFS 基础**（2 小时）：clone、commit、push、分支、LFS 追踪大文件。

**推荐资源（都是免费的）：**
- Epic 官方学习门户（dev.epicgames.com/community/learning）：搜 "Your First Hour in Unreal Engine 5"
- Epic 官方文档：C++ Programming Tutorials、Gameplay Framework 章节
- 中文：B 站搜「UE5 C++ 入门」，挑播放量高、2024 年之后、UE5.4+ 的系列
- 书籍（可选）：《Unreal Engine 5 C++ 游戏开发完全学习教程》类中文书

> ⚠️ 学习时务必注意：**UE 版本要和你项目一致**。网上 80% 的教程是 UE4 或 5.0 的，节点位置和 API 会有差异。看教程前先确认版本。

## 3. 范围管理：三档规模，先定档再开工

同一句"复刻留云借风洞天"，可以是 40 小时的项目，也可以是 800 小时的项目。开工前必须选定一档。

### 档位 A：最小可玩原型（P0）— 约 60～100 小时

- 灰盒关卡（方块 + 基础材质），不追求美术
- 玩家：跑、跳、滑翔
- 机关：风场、移动平台、激活开关、联动开门
- 掉出地图自动重置
- 无 UI、无音频、无 VFX
- **产出：一个丑陋但完整可通关的流程**

### 档位 B：垂直切片（✅ **推荐，本项目目标**）— 约 250～400 小时

- 在 A 的基础上：美术替换、光照氛围、音频、VFX、UI 提示、检查点、终点演出
- 关卡规模：完整复刻原秘境的主要段落（可适度简化）
- **产出：发给朋友看「这是我做的」不会尴尬的 demo**

### 档位 C：高保真复刻 — 800 小时以上

- 完整机关细节、原版级美术、动画、交互反馈、粒子、镜头演出
- **不建议作为第一个项目。** 如果你坚持，先做完 B 再升级。

**👉 本企划案按【档位 B】编写，但所有任务都标注了 P0/P1/P2 优先级，你可以随时降档。**

## 4. 工作分解结构（WBS）：这个项目由哪些部分组成

| W2 | 环境与工程 | 引擎配置、项目结构、版本控制、编译链 | 5% |
| W3 | 程序框架 | 玩家角色、交互系统、机关基类、存档检查点 | 20% |
| W4 | 关卡设计（LD） | 白盒、动线、机关布置、难度与引导 | 20% |
| W5 | 美术（Art） | 模型、材质、光照、后处理、VFX | 30% |

### 5.2 从原神关卡设计中学到的 5 条可复用原则

1. **视觉先行**：玩家不用读文字，靠颜色和光就知道哪里能走、哪里能互动。原神里"可交互"通常有统一的暖色/发光语义。
2. **安全网**：垂直关卡一定要有"掉下去不会死，会被送回来"的机制。这是原神在开放世界里的核心设计，你的秘境必须复刻。
3. **一次只教一件事**：新机制先在一个绝对安全的环境里单独展示，再组合。
4. **短循环反馈**：每个小机关解开都有即时反馈（音效 + 光效 + 门开动画），间隔不超过 30 秒。
5. **节奏呼吸**：紧张段（需要操作的滑翔/跳跃）后面一定跟一段放松段（走一段路、看风景）。

## 6. 创作设计：复刻到什么程度，用什么"味道"

### 6.1 设计宣言（一句话）

> **"一座会呼吸的机关洞天：玩家不是被敌人阻拦，而是被'空间本身'考问。"**

留云借风洞天的魅力不在战斗，在于**"仙人用机关考验凡人的智慧"**这个设定。所以你的设计重点应该是：机械感、机关感、束缚与自由的对比（洞内封闭 → 乘风飞升 → 豁然开朗）。

### 6.2 氛围基调

| 维度 | 设定 |
| --- | --- |
| 主色调 | 石青灰 + 古木褐 + 仙术青蓝 / 金 |
| 光源逻辑 | 洞内昏暗靠机关自发光；越往上越亮；终点是开放天光 |
| 材质关键词 | 打磨过的青石、青铜机关纹样、垂落的藤蔓、水痕、发光的仙纹 |
| 声音关键词 | 洞穴混响、机关齿轮声、风穿过石缝、悠远笛声 |
| 情绪曲线 | 困惑 → 试探 → 掌握 → 紧张上升 → 登顶释然 |

### 6.3 机关的美术语义规范（非常重要，统一视觉语言）

定一套**统一的"可交互"视觉规则**，并严格遵守：

| 状态 | 视觉表现 |
| --- | --- |
| 可交互、未激活 | 淡淡的青蓝色呼吸光，慢速脉动 |
| 已激活 | 稳定金色光，纹样点亮 |
| 不可用（锁定中） | 完全无光，材质发暗发灰 |
| 需要玩家前往 | 细光柱 / 粒子飘向目标方向 |

> 这套规则写进 `Docs/ArtDirection.md`，做资产时对照执行。初学者最容易犯的错就是"每个机关长得不一样，玩家不知道哪个能按"。

## 7. 关卡设计：从一张纸到可玩空间

### 7.1 第一步：手绘草案（在纸上，不在电脑上）

**工具：** A4 纸 + 铅笔 + 橡皮。不要一上来就用 UE，会很痛苦。

**要画三张图，每张都画两遍（俯视 + 侧视）：**

1. **俯视图（Top-Down Map）**：整个秘境的平面布局，标出房间、走道、机关位置。
2. **立面图 / 剖面图（Elevation）**：垂直分层，这关是"洞天"，纵向结构必须画清楚。
3. **动线图（Flow Map）**：用箭头画出玩家应该走的路。**这是最重要的一张。**

**画的时候必须标：**
- 入口、出口
- 每个机关的位置和编号（M1、M2、M3…）
- 玩家视线最远能看到什么
- 哪里是"安全区"（不会掉下去）
- 哪里会掉下去、掉下去会回到哪
- 每条路的高度差（大致用"1 层 / 2 层 / 3 层"表示）

### 7.2 我为你设计的一版关卡草案（起点，待对照原版修正）

> ⚠️ 这是我基于"洞天 + 机关 + 风场上升"的通用结构设计的一版可行方案，**不是你记忆中原版的精确复刻**。请对照录像修正后再开工。但作为灰盒练习，它跑得通、好玩、覆盖了所有需要的技术点。

**核心结构：四层垂直洞天，一个"回"字形的螺旋上升。**

```
第 4 层  云台（终点）          ┌────────────────┐
         · 终点传送/对话/宝箱  │   ▓▓▓ 终点 ▓▓▓ │
                               └───────▲────────┘
                                       │ 升降梯 / 风场
第 3 层  机关厅（组合机制）     ┌──────┴────────┐
         · 双开关同时激活       │  ○       ○     │
         · 移动平台横渡深坑     │   ▓▓▓▓▓▓▓      │
         · 光束/仙纹指向        └──────▲────────┘
                                       │ 风场上升
第 2 层  风之回廊（滑翔段）     ┌──────┴────────┐
         · 空中风环加速         │  ~~~风场~~~    │
         · 落地失败区           │   ○   ○   ○    │
         · 检查点               └──────▲────────┘
                                       │ 楼梯/风场
第 1 层  入口庭（教学）         ┌──────┴────────┐
         · 教学：踩踏板开门     │  ▓ 门 ▓        │
         · 教学：激活第一个机关 │  ○             │
         · 检查点               │  ▲ 入口        │
                               └────────────────┘
```

**逐层说明：**

- **第 1 层 · 入口庭（3～4 分钟）**：封闭石室。玩家进来先看到一扇关着的门和一个发光的踏板机关。踩上去 → 门开（带音效、光效、门的动画）。教会玩家"发光 = 可交互"，以及"互动有即时反馈"。
- **第 2 层 · 风之回廊（4～5 分钟）**：开阔的垂直井。地面有深坑或水。中央有持续风场，玩家跳入风场被托起，滑翔到对面平台。空中布置 3 个"风环（Wind Ring）"，穿过它们获得加速 / 回高。这是**本关最爽的部分**，要花最多时间调手感。
- **第 3 层 · 机关厅（5～6 分钟）**：难点段。两个开关距离远，需要先激活一个、在时限内赶到另一个（或用一个移动平台把"激活信号"传递过去）。中间横着一个深坑，通过移动平台过去。这里组合了前面的所有机制。
- **第 4 层 · 云台（2～3 分钟）**：豁然开朗，天光洒下。终点是一个发光的高台，触发后播放一段简单的演出（镜头移动 + 光效 + 文字），然后展示"完成"UI。

**总时长目标：14～20 分钟（首次通关）。**

### 7.3 白盒（Blockout）制作标准流程

这是关卡设计的核心工作流，**严格按顺序做，不要跳步**：

1. **只用 BSP 或 Static Mesh 方块**搭出所有空间，全部用同一个灰白格纹材质，便于判断距离。
2. **尺寸必须符合人体尺度**——见 7.4 的尺寸表。
3. **先保证"能走通"**，再考虑"好不好看"。目标：闭着眼睛跟着路也能走到终点。
4. **立刻找一个人（或你自己隔一天）试玩**，记录在哪里迷路、在哪里卡住。
5. **反复迭代至少 3 轮**。每轮结束截图存档，方便对比。
6. **只有灰盒让你满意了，才开始替换美术资产。**

> **铁律：白盒没通过"陌生人能通关"测试之前，绝不做美术。**

### 7.4 UE5 尺度参考表（贴在显示器边上）

| 项目 | 数值 |
| --- | --- |
| 1 米 | 100 Unreal Units (cm) |
| 标准角色身高 | 约 180 cm |
| 角色胶囊体半径 | 34～42 cm |
| 角色胶囊体半高 | 88～96 cm |
| 最小可行走通道宽 | 200 cm（舒适：300 cm） |
| 最小可行走层高 | 250 cm（舒适：400 cm） |

### 7.5 引导设计（Player Guidance）——初学者最忽略的部分

原神关卡的引导是"看不见的老师"。你要复刻的不是外观，是**引导逻辑**。

| 引导手段 | 怎么用 | 强度 |
| --- | --- | --- |
| 光照 | 把该去的地方照亮，其他压暗 | 最强，优先用 |
| 颜色对比 | 目标用暖色 / 亮色，环境用冷色 / 暗色 | 强 |
| 视线框景 | 用门框、洞口、石头把目标"框"在玩家正前方 | 强 |
| 动态元素 | 飘动的粒子、飘带、风的方向 | 中 |
| 几何引导 | 地砖走向、栏杆、台阶朝向 | 中 |
| 音频 | 目标方向传来声音（3D 音效） | 中 |
| UI / 文字提示 | "按下 E 激活机关" | 弱，但必要 |
| NPC 语音 | 若做，可加旁白 | 弱 |

**测试方法：** 找一个没玩过的人，不给任何提示，看他 2 分钟内能不能找到第一个机关。找不到 → 引导失败，改。

### 7.6 检查点与失败恢复设计

垂直关卡必须回答："玩家掉下去会怎样？"

**推荐方案（简单且体验好）：**

1. 在每层入口放一个**检查点（Checkpoint）** Actor，玩家经过它时自动记录（进入触发器即激活）。
2. 玩家掉到"死亡平面（Kill Z）"以下，或掉进标记为"深坑"的体积时，触发重生。
3. 重生流程：屏幕短暂淡出（0.3 秒）→ 传送回最近检查点 → 淡入 → 播放一个轻微音效。全程不超过 1 秒。
4. **不要做"扣血"或"惩罚"**，这是学习 demo，挫败感越低越好。

**技术实现预告：** 一个 `ALyCheckpoint`（C++ 基类）+ `BP_LyCheckpoint`（蓝图设模型和特效）。

## 9. 蓝图 / C++ 协作法则（你最关心的部分，请重点读）

这一节是整个企划案的核心。读懂了它，你的疑惑就解决了 80%。

### 9.1 先破除一个误解

**误解：** "要么全 C++，要么全蓝图。"
**真相：** 商业 UE 项目的标准做法是 **C++ 搭骨架，蓝图做血肉**。Epic 自己的《堡垒之夜》《Lyra》都是这样：C++ 写系统，蓝图做具体内容。

为什么？

| 维度 | C++ | 蓝图 |
| --- | --- | --- |
| 写复杂逻辑 | ✅ 强 | ❌ 节点连线会变成意大利面 |
| 性能 | ✅ 快 | 🟡 慢一点（一般场景无所谓） |
| 迭代速度 | ❌ 改一次要编译 | ✅ 改完立刻看到 |
| 美术 / 策划易用性 | ❌ 需要程序员 | ✅ 人人能用 |
| 调试 | 🟡 要断点 | ✅ 可视化调试，能看变量值 |
| 版本控制 | ✅ 文本，好合并 | ❌ 二进制，难合并 |
| 搜索引用 | ✅ 强 | 🟡 一般 |

**结论：两者不是竞争关系，是分工关系。**

### 9.2 核心心智模型：三层结构

请把下面这张图刻在脑子里。**任何一个游戏对象，都可以拆成三层：**

```
┌──────────────────────────────────────────────────────────┐
│  第 3 层：关卡中的实例（Level Instance）                  │
│  ── 在关卡里摆放的那个具体的东西                          │
│  ── 可以覆盖参数："这个风场风力 1200，那个 800"            │
│  ── 可以替换引用："这个门用 A 动画，那个用 B 动画"          │
├──────────────────────────────────────────────────────────┤
│  第 2 层：蓝图子类（BP_ 资产）                             │
│  ── 继承自 C++ 类：BP_LyWindField : ALyWindField          │
│  ── 挂美术资源（网格体、粒子、音效）                       │
│  ── 摆组件、设默认值、做一次性表现逻辑                     │
├──────────────────────────────────────────────────────────┤
│  第 1 层：C++ 基类（A / U 类）                             │
│  ── ALyWindField : AActor                                │
│  ── 定义"风场是什么"：属性、算法、状态机、对外接口          │
│  ── 不包含任何具体美术引用                                 │
│  ── 可被任意数量的蓝图子类继承                             │
└──────────────────────────────────────────────────────────┘
```

**一句话口诀：**

> **C++ 定义"能力"和"规则"，蓝图定义"外观"和"数值"，关卡实例定义"这一处的特殊性"。**

### 9.3 判断标准：这个东西该写在哪？（决策流程）

遇到任何新功能，按这个顺序问自己：

```
开始
 │
 ├─ 这是一次性、只在某一处用的小逻辑吗？
 │   （例如：这扇门打开时播一个特定音效）
 │   → YES：写在【关卡蓝图】或【BP 事件图表】里
 │
 ├─ 这个功能需要重复使用 3 次以上吗？
 │   （例如：10 个机关都要"激活 → 发光 → 广播事件"）
 │   → YES：写【C++ 基类】，蓝图只做子类差异
 │
 ├─ 这个功能含复杂数学 / 循环 / 状态机吗？
 │   （例如：风场力计算、多开关组合逻辑、路径插值）
 │   → YES：【C++】
 │
 ├─ 这个功能只是"挂个粒子、设个材质、调个数"吗？
 │   → YES：【蓝图 / 细节面板】
 │
 └─ 拿不准？
     → 先用【蓝图】快速验证原型 → 验证成功后提取到 C++ → 蓝图改为继承 C++
```

### 9.4 具体分工对照表（贴墙用）

| 内容 | 放哪 | 理由 |
| --- | --- | --- |
| 风场的向上推力计算 | **C++** | 数学逻辑，要反复调参和复用 |
| 风场的粒子特效引用 | **蓝图** | 纯资源引用 |
| 移动平台的路径插值（Alpha 0→1） | **C++** | 数学 |
| 平台用哪条曲线 | **蓝图 / 细节面板** | 资源引用 |
| 平台的移动音效 | **蓝图** | 资源引用 |

| 门的开合动画 | **蓝图**（Timeline） | 表现层 |
| 多开关的"与 / 或"逻辑 | **C++**（SwitchGroup） | 复杂逻辑 |

### 9.5 必须掌握的 C++ 反射宏（这是蓝图与 C++ 的"桥"）

这是你最需要背下来的东西。它们决定了 C++ 的东西能否被蓝图看见、能否在编辑器里改。

```
// 1. 声明一个类，让 UE 认识它
UCLASS(Blueprintable, BlueprintType)
class LIUYUN_API ALyWindField : public AActor
{
    GENERATED_BODY()   // ★ 必须有，必须是类里第一行

public:
    ALyWindField();

protected:
    // 2. 属性：能被编辑器编辑，蓝图能读写
    UPROPERTY(EditAnywhere, BlueprintReadWrite, Category = "Ly|Wind")
    float ForceStrength = 900.0f;

    // 3. 属性：只能在类默认值里改
    UPROPERTY(EditDefaultsOnly, Category = "Ly|Wind")
    TObjectPtr<UStaticMeshComponent> MeshComp;

    // 4. 属性：只读，蓝图能看不能改
    UPROPERTY(BlueprintReadOnly, VisibleAnywhere, Category = "Ly|Wind")
    bool bIsActive = false;

    // 5. 函数：蓝图可以调用
    UFUNCTION(BlueprintCallable, Category = "Ly|Wind")
    void ActivateWind();

    // 6. 函数：C++ 有默认实现，蓝图可以覆盖
    UFUNCTION(BlueprintNativeEvent, Category = "Ly|Wind")
    void OnWindActivated();
    virtual void OnWindActivated_Implementation();   // ★ 注意 _Implementation 后缀

    // 7. 函数：纯 C++ 实现，蓝图只能调，不能改
    UFUNCTION(BlueprintPure, Category = "Ly|Wind")
    float GetStrength() const { return ForceStrength; }

    // 8. 函数：C++ 不实现，只留空壳给蓝图填
    UFUNCTION(BlueprintImplementableEvent, Category = "Ly|Wind")
    void PlayActivationEffects();
};
```

**关键区别（务必分清）：**

| 宏 | 含义 | 使用场景 |
| --- | --- | --- |
| BlueprintCallable | 蓝图能调用这个函数 | 通用功能 |
| BlueprintPure | 同上，但是"纯函数"（无副作用） | Getter |
| BlueprintImplementableEvent | **C++ 不写实现**，完全交给蓝图 | "表现层"，如播特效 |
| BlueprintNativeEvent | C++ 写默认实现，蓝图**可选**覆盖 | 有默认行为但允许定制 |

**最常用的组合模式（背下来）：**

```
// C++ 决定"什么时候"发生
void ALyWindField::ActivateWind()
{
    bIsActive = true;
    PlayActivationEffects();   // ← 蓝图里接一个"发光 + 播粒子 + 播音效"
}
```

> 这叫 **"C++ 管逻辑时机，蓝图管表现效果"**。这一个模式能解决你 80% 的协作问题。

### 9.6 其他必须知道的桥接机制

**① 委托 / 事件广播（让 C++ 通知蓝图）**

```
// 头文件里声明
DECLARE_DYNAMIC_MULTICAST_DELEGATE_OneParam(FLyOnMechanicActivated, AActor*, Mechanic);

UCLASS()
class ALyMechanicBase : public AActor
{
    GENERATED_BODY()
public:
    UPROPERTY(BlueprintAssignable, Category = "Ly|Events")
    FLyOnMechanicActivated OnMechanicActivated;   // ★ 蓝图里能 Bind Event
};
```

蓝图里就能"Bind Event to OnMechanicActivated"，实现事件驱动，避免每帧轮询。

**② 组件（把功能拆成可复用的零件）**

不要把所有逻辑都堆在 Actor 里。一个机关可以是：

```
BP_LyPressurePlate (Actor)
 ├── StaticMeshComponent    （外观）
 ├── BoxCollisionComponent  （检测玩家踩踏）
 ├── AudioComponent         （音效）
 └── ULyInteractableComponent（自制：统一的"可交互"能力）
```

自制组件 = 写一个 `ULyInteractableComponent : UActorComponent`，任何 Actor 挂上它就能交互。**这是 UE 最重要的复用手段。**

**③ 接口（Interface）**

让不同的东西以统一方式被"交互"：

```
UINTERFACE(MinimalAPI, Blueprintable)
class ULyInteractable : public UInterface { GENERATED_BODY() };

class ILyInteractable
{
    GENERATED_BODY()
public:
    UFUNCTION(BlueprintNativeEvent, BlueprintCallable, Category = "Ly|Interaction")
    void Interact(AActor* Instigator);
    virtual void Interact_Implementation(AActor* Instigator) {}
};
```

玩家只调用 Interact()，不关心对方是拉杆、宝箱还是门。

**④ 数据资产 / 数据表（把"数值"从代码里拿出来）**

```
UCLASS(BlueprintType)
class ULyWindFieldConfig : public UPrimaryDataAsset
{
    GENERATED_BODY()
public:
    UPROPERTY(EditAnywhere) float Strength = 900.f;
    UPROPERTY(EditAnywhere) float Radius  = 500.f;
    UPROPERTY(EditAnywhere) float MaxRiseSpeed = 1200.f;
};
```

好处：调数值不用编译 C++，不用改蓝图，做一个 .uasset 就能配。

**⑤ Subsystem（全局系统，5.x 推荐）**

`ULyGameInstanceSubsystem` 适合放"存档、检查点、关卡流程、成就"这类全局状态。比塞进 GameMode 更干净。

### 9.7 协作工作流实战：以"风场"为例走一遍完整流程

**Step 1 — 蓝图原型（1 小时）**
先不管 C++，用蓝图做一个风场：Actor + Box Collision + 检测到玩家就往上推。在 L_LyMechanicTest 里测试，调到手感满意。

**Step 2 — 抽象出 C++ 基类（2 小时）**

```
// LyWindField.h
UCLASS(Blueprintable)
class LIUYUN_API ALyWindField : public AActor
{
    GENERATED_BODY()
public:
    ALyWindField();

protected:
    virtual void BeginPlay() override;
    virtual void Tick(float DeltaSeconds) override;

    UPROPERTY(VisibleAnywhere, BlueprintReadOnly, Category="Ly|Wind")
    TObjectPtr<UBoxComponent> InfluenceBox;

    UPROPERTY(EditAnywhere, BlueprintReadWrite, Category="Ly|Wind")
    float UpwardForce = 900.f;

    UPROPERTY(EditAnywhere, BlueprintReadWrite, Category="Ly|Wind")
    float MaxUpwardSpeed = 1400.f;

    UFUNCTION(BlueprintCallable, Category="Ly|Wind")
    void SetActive(bool bNewActive);

    /** C++ 不实现，蓝图负责播特效 / 音效 */
    UFUNCTION(BlueprintImplementableEvent, Category="Ly|Wind")
    void OnWindStateChanged(bool bActive);

private:
    UFUNCTION()
    void HandleBoxBeginOverlap(UPrimitiveComponent* Overlapped, AActor* Other,
        UPrimitiveComponent* OtherComp, int32 Index, bool bFromSweep, const FHitResult& Sweep);
    UFUNCTION()
    void HandleBoxEndOverlap(UPrimitiveComponent* Overlapped, AActor* Other,
        UPrimitiveComponent* OtherComp, int32 Index);

    TArray<TWeakObjectPtr<AActor>> AffectedActors;
    bool bIsActive = true;
};
```

关键：**C++ 里不出现任何具体材质、粒子、音效的引用。**

**Step 3 — 蓝图子类（30 分钟）**
新建 BP_LyWindField，父类选 LyWindField（C++ 类会出现在"所有类"里）。
- 在 Components 面板加 Niagara、Audio
- 在 Event Graph 里实现 OnWindStateChanged，里面写"开粒子、播音效"
- 在 Class Defaults 里设 UpwardForce = 900

**Step 4 — 摆进关卡（10 分钟）**
拖进关卡，实例上可以覆盖 UpwardForce = 1200（这个风场更强）。

**Step 5 — 复用（0 分钟）**
后面所有风场都从 BP_LyWindField 派生或直接摆，改一次 C++ 逻辑，全部生效。

### 9.8 三条铁律（违反会痛不欲生）

**铁律 1：永远不要让蓝图"重新指定父类"，除非你做好资产可能损坏的心理准备。**
如果你已经做了一堆 BP_LyWindField，然后想把 C++ 父类改名或换继承链 —— 会触发资产重定向 / 损坏。**先在 C++ 里设计稳定，再让蓝图继承。**

**铁律 2：C++ 改了 UPROPERTY 的名字 = 蓝图里已设置的数值可能丢失。**
改名时 UE 通常能弹窗问你要不要保留引用，一定选保留。更稳的做法：**尽量不改已发布属性的名字**，要改就一次性在早期改完。

**铁律 3：不要在编辑器运行中编译 C++（Live Coding）后依赖"复杂结构变更"。**
Live Coding 只能热补丁**函数体**。改头文件、加属性、加类，必须**关掉编辑器 → 用 IDE 重新编译 → 重开编辑器**。养成习惯：
- 小改函数体 → Live Coding（Ctrl+Alt+F11）可以
- 改 .h、加类、加属性 → **关编辑器，重新 Build**

### 9.9 初学者最常见的 6 个协作错误

| 错误 | 后果 | 正确做法 |
| --- | --- | --- |
| 在蓝图里重新实现 C++ 已有的逻辑 | 两套逻辑打架，行为诡异 | C++ 写一遍，蓝图只做差异 |
| C++ 类里直接引用 BP_xxx 资产 | 循环依赖、编译不过 | C++ 只声明基类指针或 Component，资产由蓝图指定 |
| 把所有逻辑塞进关卡蓝图 | 无法复用、无法调试、无法版本控制 | 提取成 Actor / Component |
| 蓝图函数参数硬 Cast 成具体类 | 一改就崩 | 用接口 + 基类 |
| C++ 属性忘了加 UPROPERTY | 被 GC 回收 → 随机崩溃 | 所有 UObject 指针成员必须 UPROPERTY |
| 在 C++ 构造里做需要世界存在的操作 | 崩 | 构造里只建组件 / 设默认值；世界操作放 BeginPlay |

### 9.10 你项目的"默认技术决策"（照抄即可，不用纠结）

1. 所有**机关**：一个 C++ 基类 ALyMechanicBase，一个蓝图子类。
2. 所有**可交互物**：实现 ILyInteractable 接口。
3. 所有**需要广播的事件**：用 DECLARE_DYNAMIC_MULTICAST_DELEGATE。
4. 所有**表现**（特效、音效、动画）：BlueprintImplementableEvent。
5. 所有**可调数值**：UPROPERTY(EditAnywhere) 或 DataAsset。
6. 所有**全局状态**：GameInstance Subsystem。
7. 所有**输入**：Enhanced Input（C++ 绑定函数，蓝图配 IMC）。
8. 所有**UI 触发逻辑**：C++ 调用，Widget 蓝图负责显示。

- 拍一块**有青苔的石头** → 生成岩壁贴图（洞天最需要）
- 拍**斑驳的木板 / 旧木门** → 生成木材质
- 拍**石阶、砖墙** → 生成地面材质
- 拍**公园里的石雕 / 铜器** → 机关底座

**优点：** 独一无二的资产，完全原创，无版权问题，质感比 AI 生成好一个数量级。
**缺点：** 生成的是高模 + 大贴图，需要 Blender 减面、需要在 UE 里转成可平铺材质。

> 建议：做美术阶段时，花一个下午去户外拍素材，回来做成 5～8 个材质。这是性价比最高的美术投资。

### 10.5 Blender 在本项目中的定位

**不要用 Blender 建整座洞天。** 你的 Blender 用法应该是：

1. **模块化套件（Modular Kit）**：做 8～12 个可重复拼接的构件——墙段、柱子、拱门、平台、栏杆，用它们拼出整座洞天。这是场景美术的标准做法。
2. **改 AI / 下载的模型**：修拓扑、调比例、换 UV。
3. **做小道具**：石灯、香炉、机关球、屏风、旗帜。
4. **减面 / 烘焙法线**：把高模变成可用的游戏模型。

**Blender → UE 导出清单：**
- 单位设为米（Scene Properties → Units → Metric, Scale 1.0）
- 应用所有变换（Ctrl+A → All Transforms）
- 原点（Pivot）放在合理位置（墙的 pivot 放底部中心）
- 至少一套 UV
- FBX 导出勾选 Apply Scalings: FBX All、Y up
- 命名规范同 8.3

### 10.6 美术工作流（美术阶段的顺序）

```
1. 从 Megascans 拉岩石 / 岩壁 → 替换白盒的墙
2. 自制模块化建筑套件（Blender）→ 搭出主要空间
3. 铺地面材质 + 贴花（Decal）增加细节
4. 摆道具（石灯、供桌、机关装饰）
5. 打光（Lumen + 少数聚光灯 + 发光材质）
6. 加雾（Exponential Height Fog）营造洞内空气感
7. 后期处理（Post Process Volume）：调色、暗角、Bloom
8. 加 VFX（Niagara：尘埃、风、机关光效）
9. 整体通盘走一遍，修穿帮和比例问题
```

> **重要：** 美术阶段一定要**先做完一整个房间**，看效果满意了再推广到全场。不要每个房间做一半。

## 12. 环境搭建实操（照着做就行）

### 12.1 第 0 步：磁盘与引擎检查

1. 打开 Epic Games Launcher，确认 **UE 5.5** 已安装（在 E:\UE_5.5）。
2. 确认 UE 5.5 自带的 **Editor Symbols for Debugging** 可以不装（占空间，初学不需要）。

### 12.2 第 1 步：创建项目（关键：选对模板）

1. 打开 Unreal Engine 5.5。
2. 选择 **Games** → **Third Person**。
3. 右上角把 **Blueprint 改成 C++**（这一步最关键，容易漏！）。
4. 设置：
   - Project Name: LiuYun
   - Location: E:\UE_projects（**不要放 C 盘**）
   - 勾选 **Starter Content**（有免费基础资产）
   - 关闭 **Raytracing**（4060 Laptop 跑不动，用 Lumen 就行）

### 12.3 第 2 步：把缓存迁到 E 盘（解决 C 盘爆满）🔴

**方法 A：改引擎的 BaseEngine.ini（推荐）**
用文本编辑器打开 `E:\UE_5.5\Engine\Config\BaseEngine.ini`，找到 `[InstalledDerivedDataBackendGraph]` 段，把 `Path=` 改成：

（E 盘根目录若没有该文件夹会自动创建；也可以放 `E:\UE_Build\DDC` 这样更整洁。）

**方法 B：用环境变量**
系统环境变量新增：
```
UE-LocalDataCachePath = E:\UE_Build\DDC
UE-SharedDataCachePath  = E:\UE_Build\DDC
```

**方法 C：编辑器内设置（最简单）**
Edit → Editor Preferences → 搜索 Cache → 把本地缓存路径改到 E 盘。

**同时处理：**
- Windows 磁盘清理 + 清空 `%LOCALAPPDATA%\UnrealEngine\Common\DerivedDataCache`（如果已产生）。
- Windows 设置 → 系统 → 存储 → 打开"存储感知"，让它自动清理临时文件。
- `C:\Users\19188\AppData\Local\Temp` 也要定期清。
- 最终目标：**C 盘保留至少 30 GB 空闲。**

### 12.4 第 3 步：解决编译器问题

你的 VS2022 是 17.14，MSVC 有 14.36 和 14.44 两个版本。UE 5.5 对 14.44 可能有兼容性警告。

**方案 1（推荐，最简单）：先试。**

**方案 2：指定 MSVC 版本。**
在项目目录下创建 `Build\LiuYun.Target.cs` 同级或项目根目录，UE 支持用 `E:\UE_5.5\Engine\Build\BatchFiles\Build.bat` 时加参数。更常用的做法是在 `Engine\Config\Windows\WindowsEngine.ini` 里设置允许的工具链版本范围。

**方案 3：用 14.36 工具链生成项目。**
在 Visual Studio Installer 里确认装了 14.36 的组件，然后用"工具链版本选择"（VS 安装器 → 修改 → 单个组件），或者直接在 VS 里：项目属性 → 常规 → 平台工具集 → 选 14.36。

**方案 4：如果实在不行，退到 UE 5.3。**
你机器上也有 5.3，兼容性更老、更稳。代价是少一些 5.5 的新特性（本项目用不到）。

> 我的建议顺序：**先试 UE 5.5 默认编译 → 报错 → 按方案 3 换 14.36 → 还不行再考虑 5.3。**

## 13. 各机关 / 系统的技术方案（逐个拆解）

这一节回答"每个机关具体怎么写"。每个机关都给出：**职责、C++ 类设计、蓝图做什么、关键参数、常见坑。**

### 13.1 公共基类：ALyMechanicBase

**为什么要有它：** 所有机关都有共同点——有"激活状态"、有"激活事件"、要被关卡流程查询。抽出来就不用在 10 个类里重复写。

**C++ 类设计（LyMechanicBase.h）：**

```
UENUM(BlueprintType)
enum class ELyMechanicState : uint8
{
    Dormant,      // 未激活，不可用
    Available,    // 可激活
    Active,       // 已激活
    Completed     // 已完成（一次性机关）
};

DECLARE_DYNAMIC_MULTICAST_DELEGATE_TwoParams(FLyOnMechanicStateChanged,
    AActor*, Mechanic, ELyMechanicState, NewState);

UCLASS(Abstract, Blueprintable)
class LIUYUN_API ALyMechanicBase : public AActor
{
    GENERATED_BODY()
public:
    ALyMechanicBase();

    UFUNCTION(BlueprintCallable, Category="Ly|Mechanic")
    void SetMechanicState(ELyMechanicState NewState);

    UFUNCTION(BlueprintPure, Category="Ly|Mechanic")
    ELyMechanicState GetMechanicState() const { return State; }

    UFUNCTION(BlueprintPure, Category="Ly|Mechanic")
    bool IsActive() const { return State == ELyMechanicState::Active
                             || State == ELyMechanicState::Completed; }

    UPROPERTY(BlueprintAssignable, Category="Ly|Mechanic")
    FLyOnMechanicStateChanged OnMechanicStateChanged;

protected:
    virtual void BeginPlay() override;

    UPROPERTY(VisibleAnywhere, BlueprintReadOnly, Category="Ly|Mechanic")
    ELyMechanicState State = ELyMechanicState::Available;

    /** 蓝图实现：换材质、播粒子、播音效 */
    UFUNCTION(BlueprintImplementableEvent, Category="Ly|Mechanic")
    void OnStateChangedVisuals(ELyMechanicState NewState);
};
```

**蓝图：** `BP_LyMechanic_Base`（父类设 ALyMechanicBase），实现 OnStateChangedVisuals。
**注意：** 基类标记 `Abstract`，不能在关卡里直接摆，必须派生。

### 13.2 交互系统：ILyInteractable + 玩家交互组件

**职责：** 任何东西都能被"交互"，玩家不关心对方是什么。

**接口（LyInteractable.h）：**

```
UINTERFACE(MinimalAPI, Blueprintable)
class ULyInteractable : public UInterface { GENERATED_BODY() };

class LIUYUN_API ILyInteractable
{
    GENERATED_BODY()
public:
    /** 返回是否可以交互（比如门已经开了就不能再交互） */
    UFUNCTION(BlueprintNativeEvent, BlueprintCallable, Category="Ly|Interaction")
    bool CanInteract(AActor* Interactor) const;
    virtual bool CanInteract_Implementation(AActor* Interactor) const { return true; }

    /** 执行交互 */
    UFUNCTION(BlueprintNativeEvent, BlueprintCallable, Category="Ly|Interaction")
    void Interact(AActor* Interactor);
    virtual void Interact_Implementation(AActor* Interactor) {}

    /** 给 UI 用的提示文字，如"按 E 激活机关" */
    UFUNCTION(BlueprintNativeEvent, BlueprintCallable, Category="Ly|Interaction")
    FText GetInteractPrompt(AActor* Interactor) const;
    virtual FText GetInteractPrompt_Implementation(AActor* Interactor) const
    { return FText::FromString(TEXT("交互")); }
};
```

**玩家侧（ALyPlayerCharacter）：**

```
// 每帧（或用 Timer，每 0.1s）从摄像机做一次射线检测
void ALyPlayerCharacter::UpdateInteractTarget()
{
    FHitResult Hit;
    FVector Start = CameraComp->GetComponentLocation();
    FVector End = Start + CameraComp->GetForwardVector() * InteractRange; // 250.f

    FCollisionQueryParams Params;
    Params.AddIgnoredActor(this);

    if (GetWorld()->LineTraceSingleByChannel(Hit, Start, End, ECC_Visibility, Params))
    {
        AActor* HitActor = Hit.GetActor();
        if (HitActor && HitActor->Implements<ULyInteractable>())
        {
            // 更新 UI 提示，缓存 CurrentInteractTarget
        }
    }
}
```

**蓝图：** 玩家蓝图里放一个 `WBP_LyInteractPrompt` 的引用；接口的提示文字通过 UI 显示。
**关键参数：** InteractRange = 250～350；射线通道要包含你的交互物碰撞。
**常见坑：** 射线打到了自己的胶囊体 → AddIgnoredActor；机关碰撞体没开 Visibility 通道 → 打在墙上了。

### 13.3 踏板机关：ALyPressurePlate

**职责：** 玩家踩上去 → 激活；离开 → 可选保持 / 复位。

**设计要点：**
- 一个 Box Collision 检测重叠
- 踏板网格会下沉一小段（约 5～10 cm）作为反馈
- 参数：`bLatchOnActivate`（踩过就永久激活）、`ActivationDelay`
- 状态变化 → OnMechanicStateChanged 广播

**C++ 关键点：** 在 Box 的 OnComponentBeginOverlap / EndOverlap 里判断 `OtherActor->IsA(ALyPlayerCharacter::StaticClass())`。
**蓝图：** 设网格体、下沉动画（Timeline 或材质参数）、音效。
**常见坑：** 玩家跳过去没触发（重叠事件需要至少一方模拟物理或勾选 Generate Overlap Events）；多个玩家踩时要计数。

### 13.4 拉杆 / 开关：ALyLeverSwitch

**职责：** 玩家按 E 交互 → 激活，可做成"按一次反转状态"。

**设计要点：** 实现 ILyInteractable（Interact 里调用 SetMechanicState 切换）。
**C++：** 交互逻辑 + 状态机；**蓝图：** 拉杆旋转动画、手柄模型、音效。
**常见坑：** 交互后没更新 UI 提示；重复交互导致状态抖动（加冷却）。

### 13.5 门 / 闸门：ALySlidingDoor

**职责：** 监听一个或多个开关的激活状态，满足条件就开。

**设计要点：**
- 参数：`TArray<TObjectPtr<ALyMechanicBase>> RequiredMechanics`、`bRequireAll`（全部满足还是任一满足）
- 在 BeginPlay 里绑定每个开关的 OnMechanicStateChanged
- 每次收到事件就重新评估条件
- 满足 → 播放开门
- **开门动画建议用 Timeline（蓝图），C++ 只负责状态和条件判断**

**蓝图：** Timeline 驱动门的位置 / 旋转；音效；光效。
**常见坑：** 依赖关系在关卡里用鼠标连不方便 → 建议用一个 `ALyLevelDirector` 统一连线，或在关卡蓝图里设置；门开了但碰撞没关（要 SetActorEnableCollision 或移动碰撞体）。

### 13.6 多开关组合逻辑：ALySwitchGroup

**职责：** 把 N 个开关聚合成"全部激活 / 任意激活"。

**为什么要单独做：** 关卡 3 的"双开关"需要这个。用 C++ 写清楚比在蓝图里连一堆 AND 节点好维护。

**设计要点：** 内部维护一个开关数组，提供 `IsConditionMet()`，对外广播 `OnGroupConditionMet`。

### 13.7 风场：ALyWindField + ALyWindRing

**这是整个项目最核心也最难的机关，值得花最多时间。**

**ALyWindField（持续上升的风柱）：**
- 组件：BoxComponent（影响范围）+ 可选 Niagara + Audio
- 逻辑：每帧（Tick）遍历范围内的玩家（用重叠 + TArray 记录，比每帧 GetAllActorsOfClass 快）
- 施力方式（二选一或结合）：
  - **AddForce / AddImpulse**：物理感强，但难控制，容易飞天
  - **直接修改速度（推荐初学者）**：`Velocity.Z = FMath::FInterpTo(Velocity.Z, MaxRiseSpeed, DeltaTime, RiseLerpSpeed)`，稳定可控
- 参数：`UpwardSpeed`、`RiseLerpSpeed`、`MaxHorizontalAssist`
- 玩家离开体积时，平滑恢复重力，不要瞬间掉

**ALyWindRing（风环）：**
- 玩家穿过时给一个加速 / 回高
- 用 Sphere / Box 触发
- 有冷却，避免重复触发

**滑翔系统（ALyGlideComponent 或写在 ALyPlayerCharacter）：**
- 状态：`ELyMovementState { Grounded, Falling, Gliding }`
- 触发：在空中按空格
- 效果：降低下落速度（改为一个较小的恒定下降速度）、降低水平阻尼、允许转向
- 取消：落地、再按空格、或主动收伞
- 参数：`GlideFallSpeed`、`GlideMaxSpeed`、`GlideTurnRate`

**蓝图：** 滑翔伞模型显示 / 隐藏、风场粒子、风声（音量随风速变化）。
**常见坑：**
- 风场范围检测用 Tick 扫描所有 Actor → 卡（用重叠事件）
- 玩家在风场边缘来回抖动 → 加迟滞（进入和离开用不同阈值）
- 滑翔时能无限上升 → 限制最大高度 / 时间

> ⚠️ **重要：** 滑翔手感是这个 demo 成败的关键。**M5 请预留至少 3～4 天的反复调试时间**。参数不要写死在 C++ 里，全部做成 UPROPERTY 或 DataAsset，方便实时改。

### 13.8 移动平台：ALyMovingPlatform

**职责：** 沿两点或一条曲线来回移动，玩家站上去能跟着走。

**设计要点：**
- 用 Spline 或两个点 + 曲线插值
- 移动方式：`SetActorLocation`（简单）或 `SetActorLocationAndRotation`（带旋转）
- **玩家跟随是关键难点**：简单做法是给平台一个 Box，玩家在平台上时把玩家 Attach 到平台；但 Attach 会干扰玩家控制。更稳的做法是每帧把平台的位移量加到玩家位置（"平台速度传递"）。
- 参数：路径、速度、等待时间、循环方式

**蓝图：** 平台模型、移动音效、路径可视化。
**常见坑：** 平台抖动、玩家滑落、平台与玩家碰撞导致卡住。

### 13.9 检查点与重生：ALyCheckpoint + ULyCheckpointSubsystem

**职责：** 记录玩家到达过的最远检查点，掉出地图后传送回去。

**设计要点：**
- `ALyCheckpoint`：一个 Box Trigger，玩家进入时通知 Subsystem
- `ULyCheckpointSubsystem : UGameInstanceSubsystem`：保存 `FTransform CurrentSpawnTransform`，提供 `SetCheckpoint()` / `RespawnPlayer()`
- 掉出地图：在关卡里放一个 Kill Z 体积，或设置 World Settings 的 Kill Z
- 重生：直接 `SetActorTransform` + 清零速度

**蓝图：** 检查点激活的视觉 / 音效反馈。
**常见坑：** 重生后玩家速度没清零 → 继续往下掉；检查点被重复触发。

### 13.10 关卡流程控制：ALyLevelDirector

**职责：** 关卡是一个状态机：入口段 → 风之回廊 → 机关厅 → 云台 → 完成。

**设计要点：**
- 枚举 `ELyLevelPhase`
- 保存每个阶段的完成条件（比如"阶段 2 完成 = 玩家到达检查点 3"）
- 阶段变化时广播，UI 监听更新目标提示
- 与检查点 Subsystem 配合，实现"重生后回到当前阶段"

**蓝图：** 摆一个，配置各阶段的目标文本、触发条件（可以在 Details 里指定引用）。
**常见坑：** 流程与检查点状态不同步；阶段推进重复触发。

### 13.11 终点演出

**做法：** 用 Sequencer（Level Sequence）。
- 触发：玩家进入终点 Trigger
- 内容：镜头移动 + 光效变化 + 屏幕文字
- 播放时禁用玩家输入（Set Input Mode UI Only / 禁用移动），播完恢复或显示完成界面
**常见坑：** 演出结束后玩家不能动（忘了恢复输入模式）；演出与玩家摄像机冲突。

### 13.12 保存 / 检查点数据

本 demo 不需要完整存档系统。**只需要内存中的检查点**。不要一开始就做 SaveGame。
如果后期要做，用 `USaveGame` + `UGameplayStatics::SaveGameToSlot`。

### 13.13 UI 系统

| Widget | 职责 | 数据来源 |
| --- | --- | --- |
| WBP_LyHUD | 总容器，包含下面几个 | PlayerController |
| WBP_LyInteractPrompt | 显示"按 E 交互" | 玩家交互目标的 GetInteractPrompt |
| WBP_LyObjective | 显示当前目标 | LevelDirector 的阶段广播 |
| WBP_LyPauseMenu | 暂停 / 继续 / 退出 | PlayerController |

**常见坑：** Widget 没加到 Viewport；UI 挡住射线检测（把 Widget 的 Visibility 设为 Self Hit Test Invisible）。

### 13.14 音频系统

| 类型 | 做法 |
| --- | --- |
| 环境音 | 在关卡里放 Ambient Sound，或用 Sound Cue 做随机变化 |
| 机关音效 | 在每个 BP 的表现事件里 Play Sound at Location |
| 风场音 | 依附在风场 Actor 上的 Audio Component，音量随玩家距离 / 速度变化 |
| BGM | 用 Sound Class + Submix 控制；进入不同阶段切换 |
| 混响 | 用 Audio Volume（洞内混响是氛围关键） |

**常见坑：** 音量不统一（统一到 -6dB 左右再调）；洞内不加混响会显得"干"。

### 13.15 VFX 系统（Niagara）

| 特效 | 用途 |
| --- | --- |
| 机关自发光粒子 | 提示可交互 |
| 风场粒子 | 可视化风的方向和范围（**对玩法极重要**） |
| 激活爆发 | 机关激活瞬间的反馈 |
| 尘埃 | 洞内空气感 |
| 终点光柱 | 引导 |

**初学者建议：** 先改引擎自带 Niagara 模板（在 Content Browser 里搜索"Niagara"，有很多现成的），不要从零建。
**常见坑：** 粒子太多掉帧；粒子没开 GPU 模拟。

### 13.16 碰撞与通道（Collision Channel）

这是新手最容易卡住的技术点，单独列出来。

**建议自定义通道：** Project Settings → Collision → Trace Channels：
- `Ly_Interact`：交互射线用
- `Ly_Wind`：风场范围判断用（可选）

**规则：**
- 玩家胶囊：和 WorldStatic / WorldDynamic / Pawn 碰撞
- 机关模型：和 Pawn 碰撞（要被踩）+ 响应 Ly_Interact
- 触发器 Box：只做 Overlap，不做 Block
- 射线检测：只打 Ly_Interact 或 Visibility，避免打到墙

**调试利器：** 控制台命令 `show Collision`、`ShowDebug Trace`；在编辑器里按 P 键显示碰撞体。

### 15.2 性能目标与手段

| 目标 | 数值 |
| --- | --- |
| 分辨率 | 1080p |
| 帧率 | 60 FPS |
| 城镇 / 洞内 draw call | < 3000 |
| 视口三角面 | 视情况，Nanite 下不敏感 |

**常用控制台命令（编辑器里按 ~ 打开）：**

- `r.ScreenPercentage 70`：降低渲染分辨率（应急）

- `Slomo 0.5`：慢动作（调试手感）

**优化手段（按优先级）：**
1. 减少动态光源数量（洞内用少量点光 + 发光材质）
2. 合并静态网格（Merge Actors）
3. 用 Nanite 处理高面数静态物
4. 降低 Niagara 粒子数量
5. 用 LOD / 距离剔除
6. 关闭不必要的后期效果

### 16.1 "卡住了怎么办"——标准排查流程

1. **看 Output Log / Call Stack**（不要瞎猜），复制报错原文去搜。
2. **Google / Bing 搜索错误全文 + UE 版本号**。90% 的错别人踩过。
3. **问 AI**：把完整报错、你的代码、你做了什么贴给 AI。
4. **最小复现**：新建一个空关卡，只放出问题的那个东西，看还能不能复现。
5. **二分法**：注释掉一半代码，看问题是否消失，逐步缩小范围。
6. **回退**：`git stash` / `git checkout .` 回到能跑的状态，重新小步前进。
7. **绕过**：如果一个小功能卡了 3 天，换一种实现方式，不要死磕。
8. **求助**：Epic 官方论坛、UE 中文社区、B 站评论区、Reddit r/unrealengine。

> **3 天原则：** 任何问题卡超过 3 天，必须换方案或求助。死磕是新手最大的时间黑洞。

## 17. 每日 / 每周工作法

### 17.1 每天开工前（5 分钟）

1. 打开 DevLog，看昨天写到哪、今天要做什么。
2. 想清楚**今天唯一要做的一件事**（不要列 10 项）。
3. 打开项目，Play 一下，确认当前状态是能跑的。

### 17.2 每天收工前（10 分钟）

1. 把编辑器里的东西全部保存。
2. Play 一遍，确认没有新报错。
3. 写 DevLog（今天做了什么 / 卡在哪 / 明天第一件事）。
4. git commit。
5. 关编辑器（避免占用内存和缓存）。

### 17.3 每周（1 小时）

1. 完整通关一次，记录问题清单。
2. 整理本周遇到的问题和解决方法（可以积累成自己的"踩坑笔记"）。
3. 备份整个项目到移动硬盘 / 网盘。
4. 更新进度截图。
5. 规划下周的里程碑任务。

### 17.4 任务粒度原则

**每个任务应该能在 1～4 小时内完成，并且有可验证的结果。**

❌ 坏任务："做风场系统"（太大，不知道什么时候算完）
✅ 好任务："让玩家进入 Box 后 Z 速度平滑升到 1200"（小、可验证）
