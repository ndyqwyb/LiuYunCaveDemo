# 11 · 作品集与面试

> 项目做完不是为了自己爽，是为了让面试官在 **3 分钟内**看懂你会什么。
> 目标受众：米哈游 gameplay 程序岗 / UE 开发实习。

## 第一部分 · 作品集三件套与演示视频

**拍摄技巧**：
- **用 UE 的 Sequencer 或 OBS 录制**，1080p 60fps。
- **镜头不要乱晃**，用平滑的移动，像「用户在玩」而不是「天旋地转」。
- **每个机关展示完整的一次交互**（触发 → 反馈 → 结果），不要跳剪。
- **加字幕**（很多人静音看），字幕写「你做了什么」而不是「这是什么系统」。

## 第二部分 · README 与一页纸技术文档

### 11.4 一页纸技术文档（证明你的技术深度）

**格式：一页 PDF 或 Markdown，结构如下：**

```markdown
# 留云借风洞天 · 技术说明

## 1. 系统架构
（贴 `03_机关设计规格.md` 3.10 的分层依赖图）

## 2. C++ / 蓝图分工
| 层 | 技术 | 例子 |
| C++ | 逻辑与规则 | ALY_MechanicBase, ALY_FirePillar, ULY_InteractComponent |
| 蓝图 | 表现与配置 | BP_LY_FirePillar 的材质/粒子/音效 |
| 关卡 | 摆放与参数 | 每个方碑的 MechIndex |

## 3. 核心设计：机关抽象
- 所有机关继承 ALY_MechanicBase（状态机 + 事件广播）
- 所有可交互物实现 ILY_Interactable 接口
- 新增机关只需：继承基类 + 实现接口 + 蓝图做表现（< 100 行）

## 4. 两处谜题的实现
- 记忆顺序谜题：Manager 播放序列 → 校验玩家输入 → 广播完成
- 联动翻转谜题：环形数组 + 取模索引 + 全亮判定

## 5. 遇到的挑战与解决
1. 角度对齐浮点误差 → FindDeltaAngleDegrees + 容差
2. 风场做不成「吹飞」的 → 改成零重力匀速电梯 + 每帧写速度 + 迟滞 + 出柱还原重力
3. 移动平台附着 → 速度传递 / Attach

## 6. 性能
- 1080p / 60 FPS / RTX 4060
- Lumen + Nanite，动态光源 ≤ 8
```

### 11.5 面试话术（重点准备这 5 个问题）

#### 11.5.1 话术 1：「介绍一下你这个项目」

> 「这是一个用 UE5 C++ 和蓝图复刻《原神》璃月秘境『留云借风洞天』的垂直切片，10 分钟左右的解谜关卡，没有战斗，重点放在地图机关还原。整个项目我自己做了 12 周，从环境搭建、关卡白盒、机关系统到美术替换和打包。
> 技术上我重点练的是**蓝图和 C++ 的协作架构**：所有机关继承同一个 C++ 基类，通过接口和事件广播解耦，蓝图只负责表现。这样新增一个机关只需要继承基类、配置参数、做蓝图表现，逻辑不用重复写。」

#### 11.5.2 话术 2：「为什么用原创/免费素材代替官方资产？」

> 「这是有意为之的。第一，直接从游戏里提取资产涉及版权风险，我投的是米哈游，更要避免这个问题；第二，我的目标是练 gameplay 和工程能力，美术不是重点，所以我把预算和时间集中在玩法上，美术用免费素材和 AI 生成，全部记录在 AssetCredits 里。
> 我认为**能清楚说明『为什么不那么做』也是工程判断力的一部分**。」

> 💡 **这个回答会加分。** 它展示了你的合规意识和取舍能力，而不是「我不会建模所以凑合」。

#### 11.5.3 话术 3：「蓝图和 C++ 你怎么分工？」

> 「我的原则是**『C++ 定规则，蓝图做表现，关卡摆实例』**。
> - C++ 负责：玩家角色、交互检测、机关基类和状态机、谜题的纯逻辑算法、关卡流程总控。
> - 蓝图负责：材质切换、Niagara 特效、音效、UI 动画这些需要频繁调整的美术表现。
> - 关卡负责：摆放机关、配置每个实例的参数（比如方碑的编号）。
>
> 判断标准很简单：**如果这段逻辑需要被复用、需要被测试、或者复杂到蓝图连起来一坨线，就放 C++；如果是美术表现和数值调参，就放蓝图。**
> 具体到机关，我用一个 `ALY_MechanicBase` 基类统一状态和事件，子类只写差异逻辑。所有机关都能被关卡总控统一监听，这是复用的关键。」

#### 11.5.4 话术 4：「两处谜题的设计你能讲讲吗？」

> 「这个关卡里其实有**两处完全不同的火柱谜题**，这也是我考据原版时发现很多攻略会混淆的地方。
> - 第一处是**记忆顺序型**：系统播放一个序列，玩家要复现，三轮递增，考察观察力和记忆。
> - 第二处是**联动翻转型**：六个柱子围成环，点一个会翻转自己和左右相邻，目标是全亮，这是一个有解的数学谜题。
>
> 实现上，第一处是一个 Manager 管理序列状态和校验；第二处是一个环形数组 + 取模索引，判定全亮。**两处共用同一套火方碑基类，只是上层的 Manager 不同**，这就是抽象的价值。」

#### 11.5.5 话术 5：「你遇到最大的困难是什么？」

> 「是旋转光桥的角度对齐。我一开始用浮点数直接比较角度，怎么写都接不通，debug 了一整天。
> 后来才意识到浮点数不能直接比相等，改成了计算角度差并给一个容差范围，立刻就通了。这件事让我理解了游戏开发里**『物理/几何的边界情况比主逻辑更容易出问题』**，后来做风场、移动平台时我都会先考虑边界情况。
> 我把这些问题都记在了 DevLog 里，后来发现它们反而是我成长最快的部分。」

## 第三部分 · 面试模拟与投递

### 11.6 进阶题（大概率会问，准备要点）

| 问题 | 回答要点 |
| --- | --- |
| **为什么用事件广播而不是直接调用？** | 解耦：机关不需要知道谁在听；总控、UI、音效、成就系统都能独立订阅；新增监听者不用改机关代码 |
| **为什么机关要抽象成基类？** | 统一状态和生命周期（未激活/激活/完成），总控可以统一管理；新增机关代码量 < 100 行 |
| **碰撞通道怎么设计的？** | 有专门的 `LY_Interactable` 通道，交互射线只查这个通道，避免打到地形/角色 |
| **风场为什么不用 AddForce？** | 物理力会累积导致失控；改成「零重力 + 每帧直接写 `Velocity.Z`」的匀速电梯，速度永远可控 |
| **风场为什么把施力写在角色身上而不是风场 Actor 上？** | 两个 Actor 的 Tick 顺序不确定，会出现「时灵时不灵」；让角色推进自己的速度，时序永远是对的 |
| **风场的「控制系数」是调大还是调小？** | 调大。UE 的 `AirControl` 默认约 0.05，不改的话柱内按 W 几乎不动，「玩家自己飞到平台上」就不成立 |
| **移动平台怎么让玩家跟着走？** | 速度传递或 Attach；关键是转身/跳离时的状态清理 |
| **检查点怎么防止顺序错乱？** | 检查点带索引，只接受「比当前更新的」检查点 |
| **性能怎么优化的？** | `stat unit` 找瓶颈；动态光源 ≤ 8；Lumen 质量降档；材质实例复用 |
| **为什么不做战斗？** | 主动的范围控制：目标是练关卡与机关系统；加战斗会稀释深度，且美术成本高 |
| **怎么保证不同机关手感一致？** | 统一视觉语义（可交互=青蓝呼吸光、已激活=金色稳定光）+ 统一交互距离与反馈时长 |
| **如果让你重做，你会改什么？** | 选一个**真实的**改进点，例如「更早做打包验证」「更早找人试玩」「机关参数外置成 DataAsset」 |

### 11.7 陷阱题 / 压力题（小心，容易翻车）

| 问题 | ⚠️ 错误回答 | ✅ 正确回答 |
| --- | --- | --- |
| **「这是原神的关卡，不算你的设计吧？」** | 辩解「我改了很多」 | 「关卡结构是参考，但**机关系统的技术实现、C++ 架构、8 个流程阶段与 11 个节点的流程控制、两处谜题的算法**都是我自己设计和实现的。我把它当成**用真实关卡作为需求**的一次工程练习。」 |
| **「美术这么简陋，是不是偷懒？」** | 「我不会建模」 | 「这是**有意识的取舍**。我投的是 gameplay 方向，所以把时间预算集中在玩法与架构上。美术用统一色板 + 后处理描边 + 免费素材，做到**风格统一、能代表完成度**就够了。」 |
| **「这不就是照着教程做的？」** | 含糊其辞 | 直接讲**哪个部分是自己想的**：谜题算法的抽象、环形取模、风场速度控制、检查点索引设计。**诚实 + 具体**最有说服力 |
| **「C++ 写了多少行？」** | 编一个数字 | 说**实际的类和职责**：「十来个 C++ 类，玩家角色、交互组件、机关基类、六个机关子类、两个谜题 Manager、流程总控」——**比行数更有说服力** |
| **「你能现场改个功能吗？」** | 慌张拒绝 | 「可以，给我一个具体需求」——**这是展示能力的机会，不是陷阱**。现场演示是你最大的优势 |

## 第五部分 · 应急路线与心态

### 11.13 如果进度落后了，按这个顺序砍

**砍的顺序（从先砍到后砍）：**

1. ❌ 美术精细化（建筑模块细节、道具外观）
2. ❌ VFX 的复杂度（火焰/风用最简单模板）
3. ❌ UI 美化（用默认风格，能看懂就行）
4. ❌ 音频（**只留环境音 + 3 个机关音效**）
5. ❌ 终点演出的复杂度（改成简单对话框）
6. ❌ 角色外观（用最简单的人形占位）
7. ⚠️ 只保留 **3 个宝箱**
8. ⚠️ 只保留**一个旋转桥**（第二个改成自动开门）

**绝对不砍：**

- ✅ M0 的打包验证
- ✅ 玩家手感
- ✅ 交互系统
- ✅ 旋转光桥（核心机关）
- ✅ 两处谜题的**逻辑**（可以简化参数，但机制要在）
- ✅ 完整流程（从入口走到结算）
- ✅ 合规声明与 AssetCredits

### 11.14 如果只剩 6 周就要投简历（应急交付路线）

### 11.15 「状态不好」的时候怎么办

| 症状 | 应对 |
| --- | --- |
| 连续几天不想打开 UE | **降低门槛**：今天只做「打开项目、随便走两圈」也算完成任务 |
| 觉得做得太丑，想推倒重来 | **回看 `Docs/Progress/` 的早期截图**，你会发现自己进步很大 |
| 卡在一个 bug 上两天了 | **立刻换任务**，去做别的部分；或者把问题写进 DevLog 明天再看 |
| 觉得自己根本做不完 | **看第 8 周的应急路线**：你随时可以在任何一周停下，产出一个完整可玩的东西 |
| 怀疑这个项目对求职没用 | 回看本文件第四部分 —— **你练的这些恰恰是 Gameplay 岗最想看的** |
| 想再加一个功能 | **回去读 README 的「不做清单」**。范围膨胀是这类项目的头号杀手 |

> 💡 **这个项目的难点从来不是技术，而是「坚持到完整可玩」。**
> 你不需要做得比原神好，你只需要**做完** —— 做完本身就是极强的信号。

### 11.16 项目结束后

1. **先玩一周不碰 UE。** 让脑子冷却。
2. 把这 12 周的 DevLog **从头读一遍**，把「遇到的坑 + 怎么解决」整理成一篇技术博客/知乎回答 —— **这是你简历之外的第二个作品**。
3. 复盘：哪些地方浪费时间了？哪些决策是对的？
4. **下一个项目换一个方向**：这次练了「机关解谜系统」，下次可以练「AI 行为树」「战斗系统」「存档系统」—— **广度是求职的加分项**。
5. 把本项目的 C++ 类**重构成一个可复用的插件**，作为长期资产。
